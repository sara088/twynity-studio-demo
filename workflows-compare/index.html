Decision

Where does the workflow builder live?

We already have a Workflow Builder. The question is whether a user leaves Twynity to use it, or never notices it's a separate thing. Three options, all clickable, all running the same builder.

Option A

Native

Best experience · highest cost

We rebuild the builder inside Twynity. Our shell, our design system.

No context switch at all
One design system, one login
Full control of every detail
Rebuilds something we already own
Two builders to maintain forever
Slowest to ship
Open Native
Option C

Embedded

Recommended

The existing builder, iframed into a Twynity tab and themed to match.

Feels native — never leaves the page
Reuses the builder we already have
No export, no upload, no second copy
Theming and auth plumbing needed
iframe adds some technical constraints
Open Embedded
Option B

Launch out

Cheapest · weakest experience

Workshop links to Workflow Builder. It opens in a new browser tab.

Ships almost immediately
Zero integration work
Builder evolves independently
User leaves Twynity mid-task
Different look, different app
Work must be moved back by hand
Open Launch out
1

Why that order — the evidence

New tabs disorient people

NN/g has given the same advice since 1999: links should open in the same tab. New tabs break the Back button, and users often don't notice the switch — worst for people with attention or memory difficulties.

nngroup.com

Context switching is expensive

Switching tools costs real focus time, and the effect compounds across a day. Every hop out of Twynity and back is a place the user can stall or simply not return.

uxmatters.com

Embedding is the industry answer

Prismatic, Workato, Cyclr, Albato and n8n Embedded exist precisely to put an existing builder inside someone else's product — themed, chrome hidden, host-authenticated.

prismatic.io

Worth knowing:native-vs-iframe is genuinely contested — there are vendors whose whole pitch is “white-label builders that don'tuse iframes.” Option C is the pragmatic middle, not a free lunch. If the builder ever needs to feel truly seamless, Option A is where it ends up.

2

If we launch out: how does the work get back?

This is the part that decides whether Option B is viable. The team's instinct is download the workflow, then upload it to Twynity. That works once, and then quietly rots.

Worst

Download & upload a file

Two copies from the moment you export — nothing keeps them in step
n8n's own docs: exports omit credentials, so users re-add them by hand
Exported IDs can silently overwrite an existing workflow
Newer schemas fail to import on older versions
No run visibility — a file is a step list, not a live connection
Workable

Connect & sync via API

Connect the builder account once, then pull the flow list
One source of truth — upstream edits appear here
We already mock exactly this for n8n / Power Automate
Still two apps, still a round trip to author
Best

Embed — no transfer at all

The builder writes straight to our store
Nothing to export, so nothing can drift
Save event comes back over postMessage
Paid workflows stay run-only — never handed to the user as a file

The file approach also contradicts our own monetization plan. The Workflows & Teams brainstorm already concluded that paid workflows must be run-only on our runtime, because “anything the buyer's runtime can read, the buyer can extract — n8n's downloadable JSON proves zero protection.” Shipping a download button hands away the thing we planned to sell.

The decisive point: a file tells Twynity what the steps are, but the workflow still executes on the builder. To run it or show progress we need a live connection anyway — and once we have that connection, the file adds nothing except a second copy that drifts.
